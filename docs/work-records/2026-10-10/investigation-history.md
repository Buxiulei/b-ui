# HY2 调查与住宅生命周期演进记录

截至 2026-10-10，这条工作线已经从 HY2 关闭错误调查，推进到住宅服务发布、客户端捕获、出口身份和恢复动作的统一生命周期设计。核心原因是证据逐步表明：同一条用户请求经过多个独立边界，单条错误日志、一次外部探针或一个 active 状态都不能说明整条路径是否正确。已经复现并修复的控制面问题、原版内核的关闭边界、尚未完成的双栈保护必须分别记账。

用户已确认的方向是：**只使用上游原版网络内核，优化 Rust BUI，不维护定制内核；由服务器管理完整 IPv4、IPv6 和业务 DNS 策略。** 这项方向确认不等于全部实现或设备验收已经完成。本文归档调查过程；完整受管配置设计见[受管客户端设计](managed-client-design.md)，当前 Linux 恢复与保护实施状态以[恢复与独立双栈出口保护计划](../../superpowers/plans/2026-10-08-bui-c-recovery-guard.md)为准。

版本口径采用当前 [CHANGELOG](../../../CHANGELOG.md)：4.1.3 是已列发布日期的历史正式版本；4.1.4、4.1.5、4.1.8、4.1.9 条目仍标为未发布。候选源码、私有受控部署和 GitHub 正式 Release 是不同状态，不能互相替代。下文记录的是原报告已有的结果，本次文档整理没有重新执行网络实验。

## HY2 stream canceled error 0 到底证明了什么

`stream canceled ... error code 0` 描述的是 QUIC stream 被取消。它不能单独证明整个 HY2 隧道中断、某次请求交付成功、IPv6 泄漏或第三方服务封号。09-29 复核已经指出：日志中的 62/112 秒是连接年龄，没有证据证明同值的故障定时器；也不能只按时间邻近或 stream 编号，把 QUIC code 0 与 SOCKS 错误配成同一个因果事件。[来源：Rust 架构与网络稳定性复核](../../superpowers/audits/2026-09-29-rust-network-stability.md)。

10-03 的后续实验使用新核实的官方 sing-box 1.14.2 与官方 Hysteria 2.12.3，运行于仅回环可达的隔离 Linux 环境，没有运行 BUI Rust 服务。三个配置臂依次为 `sniff=true/rewrite=true`、`sniff=true/rewrite=false`、`sniff=false/rewrite=false`；短场景同时覆盖原始 IP 和原始域名请求，实际分支经过核对。

| 业务场景 | 实际次数 | 目标与客户端实际收到的数据 | 该类 code 0 日志 | 业务判定 |
|---|---:|---|---:|---|
| 普通完整响应 | 18 | 每次响应 524301 字节，摘要完整 | 0 | 18 通过 |
| 客户端结束上传，再等延迟响应 | 18 | 目标收齐 139275 字节并见 EOF；客户端响应为 0；目标随后出现 BrokenPipe | 0 | 18 失败 |
| 目标关闭发送方向，客户端继续上传 | 18 | 客户端已收齐 524301 字节；其后本地 sendall 返回成功，但目标收到的后续上传为 0 | 18 | 18 失败 |
| 双向持续活动 135 秒 | 3 | 每方向 271 个 8 字节顺序帧，共 2168 字节，顺序与摘要完整 | 活动期间 0 | 3 通过 |

合计 57 项完成，21 项业务通过、36 项业务失败。实验返回非零，独立复核返回成功只表示结果与原始证据一致，不能把 36 项交付失败改写为“回归通过”。此前一次启动失败未执行业务场景，保留为独立基础设施失败，没有计入这 57 项。

这组反例建立了三个边界：

- 没有该 ERROR 也可能丢失完整延迟响应；出现该 ERROR 时，已经收到的响应又可能是完整的。业务交付必须以两端实际字节、顺序和摘要验收。
- 三臂结果一致，关闭 `rewriteDomain` 或整个 sniff 没有修复此次半关闭损失。原始 IP 请求在 `rewriteDomain=false` 时仍可能被 sniff 改写，不能把这个开关误称为“保留原 IP”。
- 特定关闭边界无需 BUI Rust 进程即可复现，因而不能唯一归咎于 Rust；这也没有排除 BUI 在线配置、授权、DNS、捕获或生命周期的独立缺陷。

实验仅覆盖受控明文 HTTP Host、受控 UDP DNS、回环目标和 QUIC 外层 TLS。它没有覆盖目标 TLS/SNI、公共 DNS/CDN 目标重选、真实客户端 TUN、住宅供应商或互联网丢包；客户端与服务端各自的关闭责任也尚未完全分离。不能用该实验解释每一条线上错误或证明某台机器没有泄漏。

上述完整结果表是 `native-ab-report.zh.md` 与 `independent-results-review.zh.md` 的公开归档摘录。来源身份见文末；原始流量日志和配置未公开，也未用推测补齐线上目标归因。

## 已确认的局部修复与它们的适用范围

09-28 回归复现了 sing-box 1.14.1 在同一 SOCKS5 UDP 关联中先发 IPv4、后发域名目标时的接口包装缺陷，1.14.2 在同配置、同报文下成功。这个结论只针对具体会话变化，不能扩成“旧版所有 UDP 都失败”。同期 nft 修复加入本机目的地址条件，巡检先故障切换再测速，避免因无关慢工作延迟逃生。[来源：住宅代理稳定性回归](../../superpowers/audits/2026-09-28-proxy-stability.md)，提交 `729bfb6`、`e83a939`。

09-29 的 Rust 修复解决了可复现的选择竞争、恢复迟滞和策略学习误分类。只有 SOCKS REP2 可以确认规则拒绝；REP4 等网络失败保留为未知，不能直接学成永久直连规则。策略入口按稳定供应商 UUID 放在实际选择之后，避免借槽后继续使用原槽或全局 selected 的规则。[来源：Rust 复核](../../superpowers/audits/2026-09-29-rust-network-stability.md)、[出口策略验证](../../superpowers/audits/2026-09-29-egress-policy-validation.md)，提交 `7d43826`、`852fac0`。

出口策略验证使用生产 Rust renderer 和真实内核，覆盖热切保留旧 TCP、UDP 双向与同关联、半关闭、HTTP/SOCKS 混池及原始域名语义。它同时记录了成本：回环策略层增加文件描述符；IP-only 且有自动域名策略的 server-first 场景可能多等约 300 ms。结果来自单机模拟对端，不能当成公网吞吐或延迟保证。

此前的客户端业务直连规则修正是局部故障的历史处置：当时证明了特定资源分流遗漏和修正后的实际 route。它不再是完整受管模式的架构目标。用户后来选择默认双族业务与 DNS 经获准出口，新增临时业务直连例外不能替代完整捕获与故障拒绝。

## 为什么住宅必须有一个生命周期所有者

出口选择、配置发布、服务激活和授权恢复原先各有成功信号，但它们不是同一个完成条件。Clash PUT 成功只说明某次请求返回；配置写盘只说明磁盘字节存在；systemd start 返回也不保证完整 gate 已恢复。另一个写者如果在中间重启、轮换凭据或改变拓扑，就可能让运行状态与记账状态分离。

09-30 首先把“保存热切后的默认选择”和“结构变更需要激活”分开。已确认结构和当前受管文件都一致时，只保存冷启动默认值；凭据、策略、槽或监听变更仍需要校验与激活。确认依据包括结构指纹及完整文件指纹，失败或回滚不能确认新候选。首次引入缺少旧确认记录时，可能需要一次保守激活，不能声称升级无中断。[来源：激活生命周期设计](../../superpowers/specs/2026-09-30-relay-activation-lifecycle-design.md)及[实施计划](../../superpowers/plans/2026-09-30-relay-activation-lifecycle.md)。

代际实验进一步验证了稳定 front、A/B 后端、单调 generation、UUID 归因、部分发布及旧 TCP/UDP 保留。但公开 API 对未完成 SOCKS 握手和在途拨号有盲区：旧连接表空了，旧拨号仍可能抵达旧实例。因此“连续多次 API 为零”不能授权停止、复用端口或回收 bank。协议基础尚未接入生产 reconcile/watchdog；自定义 dispatch gate 只是后续候选，不能写成已采纳并交付的架构。[来源：代际配置设计](../../superpowers/specs/2026-09-30-relay-generation-contract-design.md)及[实施计划](../../superpowers/plans/2026-09-30-relay-generation-contract.md)，提交 `bc1de58`、`b45acd7`。

10-01 接受的收口是住宅专用 Rust owner：

```text
准备候选并用实际候选内核校验
  → 严格持久化 prepared
  → 发布配置、共享二进制和已发布拓扑绑定
  → 激活并观察稳定进程实例及预期监听
  → 按最新授权关闭拒绝门、恢复允许门、完整读回
  → 严格持久化 active，再确认 keys
```

daemon 与离线 CLI 使用同一机器 lease，在线命令交由现有 owner；请求取消不释放仍在写盘或执行服务动作的所有权。watchdog、API、证书与恢复消费同一已发布拓扑绑定；显式维护 stop 不被自动撤销。回滚需要验证旧配置与当前授权，不能把 recovered-old 记成新配置已激活。Unknown 的监听、实例、规则或门位观察不构成成功，也不自动授权重启。[来源：住宅 owner 设计](../../superpowers/specs/2026-10-01-residential-lifecycle-owner-design.md)及[实施计划](../../superpowers/plans/2026-10-01-residential-lifecycle-owner.md)。

这个 owner 解决控制写者与激活确认问题；门位正确仍不等于供应商、客户端和任意业务请求健康。维护重启仍可能损失现有连接，也没有启用 relay generation bank。

## 原版内核决策如何替代早期试验

早期探查过关闭边界实验修改、额外计量标签构建和新的内部转发边界。它们可以帮助定位接口能力与成本，但用户最终明确选择“只使用上游原版内核，优化 Rust BUI，不维护定制内核”。历史修改不再构成交付许可；早期记录中的“stock”字样也必须结合真实二进制来源解释。

10-03 原版控制面审计纠正了一个关键身份问题：既有发布流程使用上游 1.14.2 源码加 `with_v2ray_api` 标签自行构建，审计未发现发布脚本注入半关闭源补丁，但这仍不等于官方发布归档中的原件。版本字符串相同不能替代 archive 与裸 binary 摘要验证。此前对该构建执行的真实测试仍有效，只能支持其实际构建对象，不能追认成新下载的官方二进制测试。

现有住宅计量依赖旧 V2Ray API。源码审计指出，官方原件缺少该额外构建能力时，保留旧配置会初始化失败；单纯删掉配置又会丢失逐用户用量来源。因此切换官方分发来源前，需要验证计量和撤权迁移，不能只换下载地址或 SHA。原版新 API 的连接事件、显式用户身份与累计字节提供了候选接口，但关闭历史有限、队列可能丢事件，不能据此承诺任意断线和负载下无损计费。

这部分是 `official-binary-control-audit.safe.md` 的源码审计结论；它提出的 G0 真实运行门槛没有在该报告中执行。G0 要求区分业务交付与 API 读计数，覆盖事件重复、断链、历史溢出、关闭尾部、消费者/核心退出，以及无法恢复计量时的实际拒绝。官方来源、控制能力和业务完整性必须一起验收。后续工作不能因为这一前置难题回到长期维护定制核，也不能删除计量要求后称迁移完成。

## 捕获、外层连接与出口能力必须分开

| 维度 | 需要证明什么 | 不能从什么推出 |
|---|---|---|
| 客户端 capture | 原始应用 IPv4、IPv6 和业务 DNS 实际进入受管路径，或按合同拒绝 | 不能由“节点订阅成功”“TUN 存在”或显式 SOCKS 请求成功推出 |
| 外层 transport | 客户端经哪一种地址族连接代理服务器 | 外层 IPv4 不等于只能访问 IPv4 目标；外层 IPv6 也不等于业务已双栈捕获 |
| VPS exit | VPS 实际能以获准身份到达哪些目标族和协议 | 控制台分配地址、接口存在或一次 ping 不能证明全部业务可用 |
| 住宅 exit | 选定供应商的 IPv4/IPv6、TCP/UDP 能力及实际出口身份 | VPS 双栈成功不能替代住宅能力；住宅失败不能换成 VPS 后仍报住宅成功 |
| OS 断开保护 | 核心停止、网络切换、后出现 IPv6 时仍受管或明确阻断 | 服务端完整 JSON 无法单独保证客户端退出后物理路由不恢复 |

10-03 只读现场记录确认当时客户端有效 TUN 仅 IPv4，同时没有可用公网 IPv6 的证据。正确结论是“未完成双栈接管，未来出现 IPv6 时没有接管保证”；不能将其升级为“当时已发生 IPv6 泄漏”。同理，配置中有 direct 规则不证明当时某业务已命中该规则，仍需实际 outbound、目标观察与物理路径证据。

当时完整订阅的双族 TUN 配置会拒绝 IPv6 目标，这属于“捕获后阻断”，不是“IPv6 业务已正常代理”。旧检查把任何 IPv6 回显视为泄漏、把回显失败视为安全，也不足以应对真正代理 IPv6 出口或检测站不可达。现在的验收目标改为：明确获准出口身份、真实可达对照、实际捕获与拒绝/交付结果共同成立。4.1.8 的服务端地址族策略和 4.1.9 的客户端恢复候选在 [CHANGELOG](../../../CHANGELOG.md)中已明确分开。

## 在线用户、连接、会话与设备数的区别

在线统计也经历了同样的证据边界收口。当前仓库的 [traffic.rs](../../../crates/bui/src/modules/panel/traffic.rs#L20) 明确区分三种来源：原生 HY2 返回会话数，住宅 Clash API 返回连接条数，Xray 则按最近一段时间是否有流量增量判断在线。它们的量纲不同，直接相加不能叫“在线设备”。

目前可由源码确认的行为是：`tick` 在写入面板缓存之前，将同一用户归一为 0/1；任一来源有在线证据，该用户只计一次，汇总表示在线用户数。[实际归一实现](../../../crates/bui/src/modules/panel/traffic.rs#L425)与同文件 `the_panel_counts_one_online_user_not_the_sum_of_three_dimensions` 回归用例分别保存实现和判据。该用例同时构造多个 HY2 会话、多条住宅连接及 Xray 增量，要求仍为一个在线用户；本次只读核对了这些源码，没有重新运行该测试。

这不是“已识别每一台设备”的实现证据。同一公网 IP 可以是多台 NAT 内设备，单台设备也可能建立多条连接或会话；现有连接 UUID、会话数、来源 IP 和用户凭据都不能自动成为稳定设备身份。后续官方 API 的显式用户和连接事件可以改善归户，但没有据此证明 NAT 内设备去重。没有独立设备身份与真实验收前，应继续准确展示用户、会话或连接各自的口径，不能虚构已完成精确设备计数。

## 已接受主线与当前未完成部分

完整 profile 的方向已获用户确认：一个 Rust 策略模型、一个授权快照、明确客户端 target，统一生成捕获、DNS、出口与失败策略。首个第三方交付目标是固定版本的 v2rayN/macOS；bui-c 复用策略语义；Android/iOS 按真实消费能力与设备验收分别推进。服务器策略交付与客户端 OS 权限是不同边界，首次 VPN/TUN 授权仍由用户完成。详见[受管客户端设计](managed-client-design.md)。
