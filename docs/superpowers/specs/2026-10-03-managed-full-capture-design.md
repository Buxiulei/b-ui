# BUI：服务器管理的完整代理配置 — 架构提案

状态：用户于2026-10-03审阅批准的架构方案；尚未实施或部署。2026-10-03，Asia/Shanghai。
源码基线：2676acdc161a409939f778bafa7e6356eba1aec4，候选版本4.1.6。

## 1. 用户目标与交付定义

用户要求 BUI 坚持 Rust 管理控制代码、只使用官方原版网络内核；sing-box 只针对1.14.2。默认从服务器拉取完整配置并由服务器管理策略，避免用户分别在 v2rayN、v2rayNG、Shadowrocket 手工维护大量 DNS、路由及 IPv6 设置。应用的 IPv4、IPv6、业务 DNS 经选定代理出口；住宅出口失效时拒绝，不回落本机或 VPS 身份。继续追查 HY2 关闭错误，不以静音日志、Mac 域名直连例外或频繁重启代替修复。

“全接管”的验收对象是受支持应用的公网业务流量，包括无代理环境变量的原始 socket。系统 VPN 建链、DHCP、邻居发现等必要控制通信单独列出；localhost 不送往远程服务器，局域网目标默认拒绝，不能把整个私网直连规则混入业务默认策略。平台强制保留的系统例外必须如实说明。

初次导入和 OS VPN/TUN 权限授权不可省。客户端不能接受完整策略时，不将节点列表显示为全接管。用户退出 VPN 后是否阻止直连属于独立 OS 保证，不能由服务器配置承诺。

## 2. 已证实的现状

- `/api/sub/<token>` 只返回节点 URI；没有 TUN、DNS、路由或客户端自动更新设置。
- `/api/subscription/<token>` 返回完整 sing-box JSON，已有双栈 TUN 地址，却拒绝所有 IPv6 目标并强制业务 DNS `ipv4_only`。
- bui-c 的 TUN 与订阅 renderer 各自维护策略，只有检测到物理 IPv6 才添加 IPv6 TUN，还存在业务 direct 例外；nettest 将任何 IPv6 回显当泄漏。
- native HY2 的服务器出站固定 `mode: 4`；当前读取的服务器没有 global IPv6 地址或 IPv6 默认路由。控制台分配 /64 并不代表系统已激活。
- residential Verified 记录单个出口 IP 等，不具备地址族 × TCP/UDP 的实际能力证明。VPS 具备 IPv6 不能替代住宅 IPv6。
- v2rayN7.25.4 支持完整 sing-box JSON Custom 订阅并复制原配置运行；更新成功可触发核心 Reload。Mac TUN 提权、订阅自动更新仍是首次本地动作。
- v2rayNG2.2.6 完整配置为 Xray，不是 sing-box；VPN IPv6、DNS、LAN绕过与定时器在本地 VPN 层。Shadowrocket 官方明确支持远程规则配置、IPv6、加密DNS，但完整接管字段尚未经设备验收。
- 当前 Mac TUN 仅 IPv4；当前物理网络也未证实可达公网 IPv6。因此已证实捕获缺口，尚未证实当前真实 IP 泄漏，更未证明 Claude 封号因果。

依据是2026-10-03独立双栈审计、固定客户端官方源码能力核查、生产脱敏字段读回与native配置源码审查；原始审计产物留在该任务私有诊断目录。这些核查是版本固定的资料/现场证据，不等于三平台端到端验收。

## 3. 选择的架构与替代方案

建议采用：一个 Rust 策略模型 → 一个授权快照 → 按明确客户端目标输出完整配置。继续使用现有 lookup / publication_permit / nodes_for 的授权真源，不另外维护一份客户端权限数据库。sing-box1.14.2 的业务 DNS、路由和失败策略由统一 compiler 提供；bui-c 与 v2rayN 只附加平台启动参数。

独立为各客户端堆模板的方案容易重新出现 DNS/IPv6/失败策略分歧，不选。要求所有用户换成自研客户端可以加强 OS 管理，但会新增 Mac/Android/iOS VPN 产品与权限工程，超出当前最小交付，不选。现有第三方客户端以其真实能力消费统一策略，不维护通用旧版本兼容层。

## 4. 核心边界

### 4.1 CapturePolicy

默认 `managed_full`：IPv4、IPv6 公网业务都捕获；DNS经选定授权出口；无国家、域名、业务端口或业务进程 native direct 规则。捕获与出口能力分开，即使外层节点只用IPv4，也可经隧道发送IPv6目标。

必要代理建链使用核心的接口选择/独立拨号机制防止递归，不能用“整个 sing-box 进程直连所有目标”作为无限例外。节点地址 bootstrap 只用于节点拨号；业务域名必须使用代理内的 resolver。IPv6内核完全禁用等真实平台限制要明确拒绝管理模式，不静默降级为部分接管。

### 4.2 SelectedEgress 与 EgressCapabilities

账户保存由管理员明确指定的默认出口身份，profile按该默认值交付；用户不需要自行配置路由。新建账户时完成默认出口绑定。已有账户仅从已有明确身份设置迁移，多种权益共存而无明确默认时要求管理员一次指定，不根据速度或节点顺序猜测。用户/管理员选择的是一个明确出口身份，不是随意混合所有已授权节点的集合。可用传输只能在该身份允许的组内恢复；住宅故障不能切 VPS，不能因为延迟更低跨身份切换。

能力记录覆盖 IPv4/IPv6 × TCP/UDP，并区分 declared、observed、unsupported、unknown。实际验证记录出口身份、观测时间、expires_at和验证的服务路径/协议范围；过期证据视为unknown，供应商绑定、端点或出口身份变更使旧证据失效。单个443探测不证明全部TCP端口或UDP能力，不把curl返回任意IPv6当代理成功。服务端族×协议的准入目前尚未实现，需要与客户端compiler一起补齐。未知或不支持的目标族/协议拒绝并显示未验收原因；不能宣称双栈正常。取得真实能力后才发布可转发的双栈策略。

服务器 native direct、relay DNS与SOCKS/HTTP上游必须消费这份能力，不能只删除客户端IPv6 reject。HTTP供应商不支持UDP时继续拒绝，不走VPS UDP。

能力观察和短时健康抖动不应每次改变客户端配置或触发重启；服务端负责运行中的拒绝与恢复，只有已审核的策略变更才生成新的发布版本。

### 4.3 ClientCapabilities

服务端使用明确 target 选择适配器，客户端 UA 只作提示，不能证明操作系统、核心版本、VPN权限或用户是否开了IPv6。首期 target 为 `v2rayn-sb1142-macos` 和复用相同policy compiler的bui-c Linux。

能力清单区分：完整配置可消费、IPv6捕获由配置可控制、首次权限动作、自动拉取机制、更新是否重启核心、VPN退出后的OS断网保护。未真机验收的目标保持“未验收”，不自动伪装成等价target。

### 4.4 FailurePolicy

业务失败默认拒绝。撤权不依赖订阅更新，应通过各协议实际 admission 与会话撤权机制收敛，旧缓存不能成为重新获取已撤销权限的依据。现有 native HY2 鉴权发生于 QUIC 登录；kick 标记在下一次流量时生效，不能宣称每条新stream都重新鉴权。已有QUIC中的新stream、已有UDP与已有TCP如何撤权，是本方案必须设计并实证的准入边界。订阅拉取失败、旧缓存仍在和业务连接继续运行三者分别观察，不把HTTP503等同于旧连接已经消失。

现存连接撤权是否可立即终止，依据服务端实际会话控制能力单独验证；不能承诺仅改账号状态就能即时切断已经建立的全部流。没有OS阻断能力的第三方客户端被关闭时，不承诺本机仍断网。

## 5. 交付接口与发布行为

保留四个现有端点的载荷含义。新增明确target的完整配置入口（拟定：`/api/profile/<token>/<target>`），页面默认展示“完整受管配置”；URI列表标为“仅节点”。目标是改变默认交付方式，不强行让第三方应用把节点列表理解成系统策略。

发布记录包含：稳定profile名称、策略schema、策略revision、target、固定core要求、选定出口、内容摘要以及客户端必须一次完成的动作。revision仅由实际语义变更递增，BUI软件version与策略revision独立。完整配置体必须是目标客户端可解析的原生对象，元数据通过现有页面/响应头或受控manifest给出，不把额外包装对象塞进sing-box JSON。

所有完整profile基于一个一致快照生成，不拼接不同状态的节点与策略。现有 publication_permit 保护取快照阶段；lookup返回后锁已释放，renderer运行在锁外，因此它本身不会在HTTP发送前再次拒绝变化的授权。若交付要求发送前仍可发布，必须显式复核generation/revision并定义其失败行为，不能把现有mutex称为响应fence；业务最终授权仍由服务端会话控制执行。客户端缺少必要能力时返回明确不能交付原因，不回落nodes-only后声称全接管。

响应确定性：同一授权快照、策略revision和target得到完全相同的字节；不加入生成时间、随机备注或每次探测值。可提供ETag和条件请求，但只有消费端验证会正确跳过重载后才声称无变化不重启。

v2rayN官方路径更新成功会Reload，因此默认不采用秒级/分钟级订阅轮询；首次设置较长更新周期，并在发布变更时说明连接可能重建。服务端撤权收敛不依赖这个周期。BUI自管客户端先比较内容摘要，再校验、原子切换、重载与回滚；不变则不动运行进程。回滚只能恢复仍获准的旧版本，已撤权策略不得作为恢复可用性的退路。bui-c先复用策略语义，Linux OS保护作为单独真实验收，不要求它成为Mac首个完整交付的前置。

更新控制通道：初始化无代理时必须能取得本账户配置；运行中优先在授权隧道中取得。第三方应用自己的失败后直连下载行为不可由JSON完全替换，须披露并验收。此类有限控制通道不应扩张为业务direct。

订阅token及配置含凭据，只经HTTPS交付，不记录完整URL/正文，不进入公开报告、git或控制台日志。按当前账户机制轮换、撤销；未知target不会改变授权。ETag按账户target隔离，响应不能被共享缓存混给不同账户。

## 6. 客户端使用流程

v2rayN/macOS 首期：用户从BUI复制完整配置订阅URL → 导入并更新 → 选中稳定名称的完整配置 → 首次开启TUN并授权 → 一次启用订阅自动更新。后续DNS、路由、节点与出口策略由服务器发布，用户不逐项编辑配置。必须实际验证Custom配置里的IPv6TUN被权限正确加载、刷新后选中项保持、系统代理环境无关的socket被捕获。

v2rayNG/Android：完整Xray适配属于第二个独立交付目标，并明确附带首次VPN/IPv6/更新设置，以及本地LAN和分应用绕过检查；局部VPN绕过未收口时不能显示全接管。不能把v2rayN sing-box JSON直接发给它。本轮保留官方能力调查，不扩展sing-box旧版本兼容，不维护定制内核；未完成目标实现和设备验收前不显示已支持完整接管。

Shadowrocket/iOS：节点订阅和远程规则配置是不同交付物。必须在设备验证完整字段及更新生命周期后才能启用受管target；不采用来源不明的CONF样例。首期页面明确“待设备验收”，不误导用户。

这不是把大量配置工作交给用户：用户仅执行第三方应用/OS不允许服务器代做的首次授权与有限开关，业务策略由BUI维护。

## 7. 双栈服务端网络前提

服务器外层连接偏好、客户端IPv6捕获、VPS IPv6出口、住宅供应商IPv6出口是四项独立能力。

当前控制台提供的6in4数据只证明分配意图。下一步服务端验证方案必须先记录地址、路由、防火墙、MTU和持久化方式，准备可恢复的变更；采用人工6in4配置与整机停机重启属于不同运维操作，不默认执行用户粘贴的命令，也不修改当前生产自动更新或tmux。

在VPS双栈可用后，验证原生TCP/UDP/AAAA-only与DNS身份，再开放该VPS直连授权profile的IPv6业务。住宅必须通过自己的供应商双栈路径验证，VPS IPv6成功不得扩张住宅profile能力。6in4路径还需验证MTU/分片及故障阻断，不能以ping一次成功当发布依据。

## 8. HY2错误与本次架构的关系

code0是QUIC stream被对端以应用码0取消的事实，不能单独推出IP泄漏、整个隧道断联或业务成功。当前官方发布内核A/B覆盖普通完整响应、双向半关闭、135秒活动流；三臂只变sniff/rewriteDomain。IP请求在rewriteDomain=false时仍可能被sniff重写，原域名对照才隔离rewrite开关；完全关闭sniff是另一个因素。

本轮实验只覆盖受控HTTP Host、UDP DNS和loopback，尚不代表线上TLS/SNI、公共DoH或MacTUN。结果必须按业务实际字节、hash、stream身份与ERROR分别报告。配置确有缺陷才修改Rustrenderer；如果三臂都发生相同业务损失，不能将修改sniff包装成关闭边界修复。

不修改官方网络内核、不屏蔽ERROR、不用本机域名直连规避症状。若上游关闭边界无法由正确配置解决，保留最小官方版复现和准确限制；在BUI允许的官方传输选择中评估完整性，但不能未经实测自动切换。

## 9. 验收与发布门槛

| 验收层 | 必须通过的实际判据 |
|---|---|
| Rust统一策略 | 不同入口消费同一账户/出口快照；能力unknown/撤权/住宅故障均无本机或VPS fallback；同一revision字节一致；客户端adapter不自行授权 |
| 原版1.14.2核心 | 每种生成配置明确执行check与真实启动，缺核心/openssl不能return假通过；目标family、DNS detour与回环无递归 |
| 真实网络业务 | IPv4/IPv6 literal、AAAA-only、TCP/UDP、系统DNS和应用DoH、无代理环境的原始socket均在受控目标观察正确出口；字节精确完整；能力unknown时捕获后拒绝与verified时代理成功分别验收 |
| IPv6防旁路 | 在确有原生公网IPv6地址和可达路由的上行网络验证，覆盖启动、运行、网络后续新增IPv6和退出；没有IPv6路由的现场不能算防泄漏通过 |
| 稳定性 | 半关闭后延迟响应、长活动流、网络切换、睡眠唤醒；连接重载可归因，错误和业务损失独立，不能靠ERROR数量验收 |
| 失效保护 | 授权撤销、住宅/VPS目标族不可用、订阅失败、DNS失败不回落其他身份；已有流撤权行为明确 |
| 客户端交付 | Mac完整profile真实导入/更新/权限/路由；Android/iOS分别验证后才宣称支持；拒绝“节点已更新=系统已接管” |
| 更新生命周期 | 相同内容不扰动BUI自管进程；v2rayN重载事实明确，订阅备注稳定、账号缓存与停止后OS行为真实验证 |

发布前先完成GitNexusimpact与任务回归，再跑对应package gate、原版核心gate与真实业务链，进行独立代码审查和detect_changes。版本号按实际变更发布更新version.json并写changelog。本提案不改版本、不改产品、不部署；当前4.1.6候选与生产状态不能混称。

## 10. 建议交付顺序与完成标准

先完成官方版HY2 A/B结论；随后实施统一ManagedPolicy及明确target的完整配置交付，首个真实验收对象是当前Mac v2rayN与官方sing-box1.14.2。服务端IPv6与住宅能力验证作为同一主线的网络前提，不能在IPv6未知时宣布双栈完成。Android/iOS目标按单个平台验证和交付，复用策略而非再造权限或路由数据库。

这份方案是已批准的架构范围与验收条件，尚不是已批准的执行计划。文件/任务级实施计划需审阅并选择执行方式；在此之前继续已批准的隔离诊断，停止新增产品代码和生产改动。首期完成标准包含Mac真实双族捕获、代理内DNS和未知能力拒绝态；实际IPv6转发未验收时明确未完成双栈可用。服务端能力过期的运行时拒绝必须先验证原版核心及现有生命周期owner能表达；不能表达时不开放该族或撤销对应独立服务准入，不编造每流鉴权或用高频重启实现。VPS/住宅真实IPv6能力和客户端原生双栈防旁路均通过后，才升级为双栈可用。
